# ADR — i18n en pause après refonte UI

- **Date** : 2026-05-16
- **Statut** : ✅ Accepted

## Contexte

Le projet Mohtawa cible le marché **francophone et arabophone** (Tunisie, Maghreb, France). La spec initiale prévoyait un support FR + AR + RTL dès le départ.

Le founder voulait lancer Phase 3 (i18n) après la complétion des features in-app. On a commencé à câbler `next-intl` et créer les fichiers `messages/fr.json` et `messages/ar.json` complets (~300 traductions chacun).

Au milieu du wiring, le founder a décidé de :
1. Pauser l'i18n
2. Faire d'abord la refonte UI/UX
3. Reprendre l'i18n plus tard

## Question

Faut-il abandonner totalement les fichiers messages, ou les garder pour plus tard ?

## Options envisagées

### A. Tout supprimer (next-intl, messages, i18n config)
- ➕ Repo plus léger
- ➖ Tout reperdre : il faudrait re-traduire 300+ chaînes plus tard
- ➖ Tout reconfigurer

### B. Garder l'infrastructure (next-intl installé, fichiers messages présents) mais non-câblée
- ➕ Reprise en 1-2h le jour où on relance
- ➕ Les traductions FR/AR existent déjà → simple wiring des composants
- ➖ Légère dette technique (fichiers présents mais non utilisés)
- ➖ Risque de "fichiers fantômes" si quelqu'un ne sait pas qu'ils existent

### C. Continuer l'i18n maintenant
- ➖ Conflit avec la refonte UI en cours (textes vont changer)
- ➖ Double travail si le wording évolue

## Décision

**Option B : garder l'infrastructure non-câblée**.

État au moment de la décision :
- ✅ `next-intl` installé (`package.json`)
- ✅ `i18n/config.ts` + `i18n/request.ts` créés (lecture cookie)
- ✅ `messages/fr.json` + `messages/ar.json` complets (300+ entrées chacun)
- ❌ `next.config.ts` : plugin `withNextIntl` ENLEVÉ (revert)
- ❌ `app/layout.tsx` : pas de `NextIntlClientProvider`, pas de Cairo font
- ❌ Composants : utilisent toujours les chaînes FR en dur

## Travail à reprendre (estimation ~4-5h)

Quand on relance :

1. **Réactiver le plugin next-intl** dans `next.config.ts`
2. **Wrapper le layout root** avec `NextIntlClientProvider` + Cairo font pour AR
3. **Refactorer chaque composant** pour utiliser `useTranslations()` au lieu des chaînes en dur
   - Au lieu de `"Connexion"` → `t('auth.login.title')`
4. **Switcher de langue** sur `/profile` qui pose le cookie
5. **Adapter le RTL** :
   - `<html dir>` selon la locale
   - Vérifier chaque écran (sidebar à droite, alignements text inversés)
   - Icônes directionnelles (`ArrowLeft` ↔ `ArrowRight` en AR)
6. **Tests visuels** : chaque page en FR + AR

## Pourquoi pauser maintenant ?

1. **Refonte UI en cours** : la palette, les composants, les microcopy bougent → traduire pendant qu'on bouge = double travail
2. **Validation produit > internationalisation** : on lance d'abord en FR pour valider que les francophones aiment le produit. Si oui → arabe pertinent. Si non → on a évité du dev pour rien.
3. **Time-to-market** : 4-5h d'i18n peuvent être consacrées à d'autres features qui ferment plus de utilisateurs (sharing, drag&drop, theme system...) en attendant.

## Quand relancer ?

Critères de bascule :
- L'UI est stabilisée (palette + composants fixés, pas de refonte imminente)
- On a 5-10 utilisateurs francophones qui valident le produit
- Première demande explicite d'un utilisateur arabophone OU décision business de pousser le Maghreb

## Conséquences

### Positives
- Pas de double travail pendant l'instabilité du wording
- Repo prêt à reprendre : les traductions existent, juste à câbler
- Concentration sur la validation produit

### Négatives
- Petite dette technique : les fichiers `messages/` et `i18n/` existent dans le repo mais ne sont pas utilisés
- Risque d'oublier qu'on les a (à noter dans `CLAUDE.md`)
- Les traductions FR du `messages/fr.json` peuvent diverger des chaînes en dur dans le code si le wording évolue → faudra relire avant de câbler

## Mitigation

- Mentionné explicitement dans `CLAUDE.md` section "Décisions" et dans le README de `docs/`
- Cet ADR sert de signal "ne supprime pas `messages/` et `i18n/`, ils sont là exprès"
